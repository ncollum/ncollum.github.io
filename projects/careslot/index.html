CareSlot: Helping Patients Find the Right Doctor

school, team project, web development, django, data modeling

CareSlot is a clinic appointment booking website built by a team of five for COMP 8347 at the University of Windsor. Patients can find a doctor, see open time slots and book a visit online. I owned the doctors module: the data model behind every doctor, clinic and specialty, the sample data, and the pages patients use to find the right doctor.

The goal: a patient who doesn't know which kind of doctor they need should still be able to type what's wrong, like "rash", and find someone who can help, in a language they speak, at a clinic near them.

Designing the data model

A doctor belongs to one specialty and works at one clinic, and can speak several languages, so I used two many-to-one links and one many-to-many link. Each specialty also stores a list of symptom keywords, which is what makes searching by symptom possible.

class Doctor(models.Model):
  name = models.CharField(max_length=100)
  specialty = models.ForeignKey(Specialty, on_delete=models.PROTECT, related_name='doctors')
  clinic = models.ForeignKey(Clinic, on_delete=models.PROTECT, related_name='doctors')
  languages = models.ManyToManyField(Language, related_name='doctors')
  bio = models.TextField(blank=True)
  photo = models.ImageField(upload_to='doctors/', blank=True)

I used PROTECT on the foreign keys so a clinic or specialty can't be deleted while doctors still depend on it, which keeps the data consistent. I also wrote fixtures with 12 doctors, 6 specialties, 6 languages and 3 clinics, so every teammate could load the same realistic sample data with one command.

Building the search

The doctor list page combines a free-text search with filters for specialty, clinic and language. A single search box matches the doctor's name, their specialty, or the symptom keywords of that specialty:

def get_queryset(self):
  doctors = Doctor.objects.select_related('specialty', 'clinic').prefetch_related('languages')

  self.search_form = DoctorSearchForm(self.request.GET)
  self.filter_form = DoctorFilterForm(self.request.GET)
  # A bad value in the URL is left out instead of causing an error
  self.search_form.is_valid()
  self.filter_form.is_valid()

  self.q = self.search_form.cleaned_data.get('q', '').strip()
  specialty = self.filter_form.cleaned_data.get('specialty')
  clinic = self.filter_form.cleaned_data.get('clinic')
  language = self.filter_form.cleaned_data.get('language')

  if self.q:
    doctors = doctors.filter(
      Q(name__icontains=self.q) | Q(specialty__name__icontains=self.q) | Q(specialty__keywords__icontains=self.q)
    )
  if specialty:
    doctors = doctors.filter(specialty=specialty)
  if clinic:
    doctors = doctors.filter(clinic=clinic)
  if language:
    doctors = doctors.filter(languages=language)

A few details I'm proud of:

  • Fast pages: select_related and prefetch_related load each doctor's specialty, clinic and languages in a few queries instead of one query per doctor.
  • No crashes from bad links: an invalid value in the web address is ignored instead of causing an error.
  • Remembering the patient: the last search and the 5 most recently viewed doctors are saved in the session.
  • Pagination that keeps filters: 6 doctors per page, and the page links keep the current search.

How we worked

Our team of five split the site into apps (accounts, doctors, appointments, records and articles), tracked tasks on a shared Trello board, and worked through GitHub. The doctors module had to be ready early, because the appointments app builds its time slots on top of the Doctor model.

What I learned

Good data modeling makes everything after it easier. Choosing the right relationships and delete rules up front meant the search, the detail pages and my teammates' booking features all worked without changes to the model. I also learned to think about query counts early, since a list page can quietly run dozens of queries without select_related.
